This review adds an independent file/timing audit and reconciles OpenCineCam with the earlier Pura Cinema runs. `E-OCC-*` references the attached run or inventory. `E-PURA-*` references earlier measurements with their own provenance. The current capability export and lab run share model, SDK and build fingerprint by equality check. The prior Pura report identifies the same model and SDK. ## P-UHD60-GRAPH · Profile admission tested, full-resolution recording untested

`E-OCC-007/008` request UHD (3840×2160) AVC at 60. Camera 0 advertises UHD as a texture size and fixed [60,60] as an AE range. The production UHD video tuple stops at 30 for camera 0. The descriptor computes the intersection of allowed raster, texture stream duration and encoder rate. This inventory omits per-tuple minimum duration and codec verdict, so it cannot identify which filter excludes UHD60. [Descriptor construction and gates](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/camera/src/main/java/com/librestatic/opencinecam/camera/Camera2Descriptors.kt#L63-L100) · [duration and codec tests](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/camera/src/main/java/com/librestatic/opencinecam/camera/Camera2Descriptors.kt#L347-L365).

**Confirmed application cause.** `LabProfiles` submits an unlisted tuple when a texture size and a range separately match. `startPreview` admits only a descriptor-backed tuple. With no active video profile, the ordinary SDR pipeline uses `baseViewfinderSize` → `descriptor.previewSize`, recorded as 1920×1080. The lab separately builds geometry from the requested 3840×2160. The equality guard throws before encoder selection or configuration. The reported `log-recording-prepare-failed` is a shared pipeline error prefix for this AVC path. The 640×360 buffer elsewhere in the journal is the rendered sink. ## P-1080-CADENCE · First divergence is in Camera2 timestamps

`E-OCC-002` has 241 AVC samples, 59.486 samples per track-second and zero duplicate PTS. Camera results 169→170 are consecutive and 30.247 ms apart. The same timestamp pair propagates through the GPU and muxer at 30.247 ms and the 90 kHz MP4 table at 30.244 ms. Camera audit reports one cadence outlier, zero dropped frame numbers and zero failed captures. The lab's 25 ms interval threshold is crossed; the mismatch is valid as a **timing outlier**. The label conflates repeated timestamps, long intervals and frame drops. These data establish an upstream timestamp excursion and leave its physical cause open. The short `003` idle control has 127 contiguous camera results at 16.906 ms and no outlier. Its shorter window and single occurrence prevent attributing the excursion to recording load.

`H-CAD-SENSOR` predicts a change under fixed bright illumination, stable exposure and controlled temperature. `H-CAD-LOAD` predicts concentration in GPU recording with timing pressure propagated to Camera2. `H-CAD-WARMUP` predicts concentration around graph configuration or AE settling; the observed gap is about 2.65 s into the file, which weakens an immediate startup-only explanation. Pura's recorder-only UHD60 result is a useful control for topology and cadence, with a different raster and codec. [per-result observer](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/camera/src/main/java/com/librestatic/opencinecam/camera/Camera2SessionGraphs.kt#L912-L945) · [timestamp and cadence measurement](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/app/src/main/java/com/librestatic/opencinecam/research/LabVideo.kt#L180-L217).

## P-HEVC-MAIN and P-LOG-HFR · Separate codec preparation from capture

**`012` UHD30 HEVC Main.** The hardware selector accepted the HiSilicon advertisement for size/rate, Surface and HEVC Main. The codec threw at `MediaCodec.configure` with `0x80001001`. The shared GPU pipeline explicitly reselects AVC and exposes the fallback; the file was verified as AVC High, Rec.709 limited SDR, 8-bit. Earlier Pura `E-PURA-5759920` reports valid Main8 UHD30 through Camera2 + MediaRecorder with a preview at 29.990 fps. Same component family and a different application contract. The OpenCineCam failure is evidence against that exact HEVC configure request, with the final file retained as evidence of fallback. [selector](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/media/src/main/java/com/librestatic/opencinecam/media/video/VideoEncoderSelector.kt#L160-L201) · [requested format and fallback](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/camera/src/main/java/com/librestatic/opencinecam/camera/OpenCineLogGpuPipeline.kt#L989-L1055).

**`011` OCLog2 1080p120.** The constrained graph yielded 22 contiguous Camera2 results at a median 8.517 ms, about 117.41 results/s, with [120,120] in request/readback. The source path was requested as `SDR_BT709_ISP`. The lab reports the same numeric codec exception before encoded samples existed; the exception wrapper erases the exact substage. EGL 10:10:10:2 configuration had passed for preview initialization. Encoder creation, configure, input surface, EGL window binding and start remain separate suspects. A camera callback establishes camera cadence over this short window. Unique high-rate pixels delivered into the recording surface still need proof. [HFR preview session](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/camera/src/main/java/com/librestatic/opencinecam/camera/Camera2SessionGraphs.kt#L284-L340) · [encoder window, start and failure](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/camera/src/main/java/com/librestatic/opencinecam/camera/OpenCineLogGpuPipeline.kt#L1050-L1155) · [Camera2 HFR target semantics](https://developer.android.com/reference/android/hardware/camera2/CameraConstrainedHighSpeedCaptureSession#createHighSpeedRequestList(android.hardware.camera2.CaptureRequest)).

**Highest-value format delta.** The prior working Pura DirectEncoder explicitly passed HEVC MainTierLevel51 and BT.709 limited SDR in its successful first Main10 attempt, with a 60 Mb/s request. Its constructor independently stages configure, input-surface creation and start. OpenCineCam's selector forwards no HEVC level, and its builder adds VBR and SAR keys. OCLog2 also requests BT.2020/full-range and deliberately leaves transfer unspecified. `H-CODEC-LEVEL` prioritizes the explicit level as the first reversible difference. `H-CODEC-KEYS` considers VBR/SAR/range/bitrate and their interactions. `H-CODEC-SURFACE` predicts standalone synthetic configure/start success but a producer-specific failure on input or rendering. `H-HFR-RATE` predicts Main10 fails only at 120 after identical lower-rate controls. The shared numeric error alone cannot distinguish these hypotheses. `X-02` isolates the first failing call before testing any camera. ## P-MAIN10-GEOMETRY · Coded depth passed elsewhere, picture geometry blocks use

`E-PURA-GEOM` retains independent decode of three prior Main10 originals, across both Camera2→MediaRecorder and Camera2→MediaCodec routes. The decoded left/right-half luma MAD medians are about 0.864–0.917 on an 8-bit-equivalent scale, while quarter-width comparisons are 96.151–111.680. The measurements span 103, 102 and 202 frames. `E-PURA-5698009/5710757` separately report 10/10 SPS bits and a repeat-half signature after portrait orientation in their sampled decode. UHD30 had near-30 cadence and zero long intervals in the later run. UHD60 had 57.378 fps and nine long intervals. Preserve the distinction between valid Main10 coding, cadence and faithful pixels.

The eight OpenCineCam AVC controls in this run decoded successfully across 55 software-sampled frames. Median half differences span 102.614–106.339 horizontally and 69.504–73.580 vertically at 384×216. This rules out the near-identical-half signature in those samples. It does not establish chart geometry or accuracy across all video frames. Use this matched-scene AVC behavior as a negative control for the geometry detector.

`H-GEOM-LAYOUT` prioritizes producer/consumer layout, stride, crop, chroma packing or vendor conversion because both prior Android HEVC paths exhibit the pattern. `H-GEOM-PREENC` places it in the camera/ISP stream or direct-surface usage. `H-GEOM-FORMAT` predicts reproduction with an asymmetric synthetic RGB10 producer or with a particular color/profile setting. `H-GEOM-READ` predicts a decoder/display issue, weakened by the retained independent software measurements and the orientation-dependent axis mapping. `X-03` uses a labelled non-repeating target, native decoded planes and an independently checked reference before any OCLog2 experiment.

## P-SOURCE-PRECISION · API gate, ISP path and grading latitude

On API 31 regular OCLog2/HLG/HDR10 never enters the candidate set: public dynamic profiles are API 33+, and the app also requires BT.2020 HLG color-space advertisement through the API 34 gate. HFR OCLog2 instead uses the advertised constrained stream with SDR/BT.709 ISP as its input assumption. `SurfaceTexture.dataSpace` is API-gated in the pipeline; the 640×360 RGB preview sink and EGL channel sizes do not measure camera precision. The hardware advertises HEVC Main10, which the Pura files confirm for coded depth on another graph. `E-PURA-PRECISION` observed an 8-bit grid at three prior taps with both synthetic quantization controls. Scope is those taps and sampled conditions. `E-PURA-FMTS` already records P010 session rejection and conditional RAW_SENSOR observations. RAW_SENSOR arrived in earlier trials with companion YUV and paired timestamps. Packing fidelity, values above nominal white, full-rate streaming and sustainable bandwidth are unresolved. Treat that as a distinct RAW16 investigation, with RAW10 absent from current camera 0 advertisement. Its UI mode provenance and VUI/SEI require direct comparison. `H-REGION-APP` considers stock camera mode policy and API exposure; `H-REGION-PIPELINE` considers firmware-specific ISP/HAL or privileged processing. ## P-LAB-EVIDENCE · Classifier and search audit

- All 12 outcomes reconcile with the journal summary: six matching AVC files (001, 004–006, 009–010), two preview-only observations (003, 008), two mismatches (002, 012) and two failures before media (007, 011). `010` gives the longest current positive control, 10.036 s UHD24 at 24.014 samples per track-second and 45 ms maximum presentation interval. The other positive UHD controls establish short AVC 24/25/30 operation in this exact route.
- The `002` threshold expresses an outlier, the `012` verdict correctly catches fallback, and `007/008` need an independent exact-graph verdict. `011` needs an explicit encoder substage, selected component and format. An empty pre-created clip is an artifact state. It carries no codec or file qualification.
- MP4 replay uses `mdhd` timescale and `stsz` or expanded `stts` for sample count. Expand `stts` to DTS, add signed/unsigned `ctts` offsets in decode order when present, then compare sorted presentation deltas separately. Inspect edit lists before comparing absolute origins. Match `stsd/avcC`, coded depth and `colr/nclx`; use SPS and independent decode for HEVC. In this run the video sample counts matched the Android extractor and time differences stayed below one microsecond. Use `ffprobe -select_streams v:0 -show_streams -show_packets -show_data -of json clip.mp4` or the project qualification tooling as a cross-check. Distinguish NAL/SPS profile, container profile, actual decoded pixels and effective source precision.
- Current sampling sorts PTS, stores extractor order, and bounds the extractor list at 4096 and timing arrays at 2048 without a truncation flag. `droppedObservationEvents` counts queue losses only. Record decode-order reversals separately, distinguish legal frame reordering, check duplicate/full-window PTS, and count real target buffers. Include head/tail exclusions, actual duration and an explicit truncation counter. [extractor bound](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/app/src/main/java/com/librestatic/opencinecam/research/LabVideo.kt#L221-L239) · [timing arrays and queue loss](https://github.com/zkreiaalamary-dotcom/opencinecam/blob/adc19ce1a8bc141885160b00c8bea83cca948787/app/src/main/java/com/librestatic/opencinecam/research/LabSignals.kt#L124-L162).
- Ten of twelve slots went to AVC including idle controls. The last-progress heuristic cannot return to an unresolved high-value hypothesis after a new branch, refuses lower-rate HFR follow-up after an early failure, and hides older observations behind the latest node. A range that merely contains the target can propose a candidate, while the engine applies only a fixed equivalent range in this regular path. Record why each tuple was skipped, rejected or tested and reserve slots for differential controls.
