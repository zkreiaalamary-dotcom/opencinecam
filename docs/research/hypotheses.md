### Failure A: `LOG_REGULAR_4K30` (`002`, `016`) Configured & Started, Emitted `muxer_track`, Yet Produced `0` Encoded Frames (`3,429 B` MP4)
Note critical comparison: **`003 GPU_HEVC_4K30` uses the exact same `OpenCineLogGpuPipeline` + Camera2 `TEMPLATE_RECORD` + `OMX.hisi.video.encoder.hevc` + same thread/drain loop, and SUCCEEDED (`122–124` frames, `0` drops) in all 3 runs!** Only 4 parameters changed between `003` (works) and `002` (0 frames): `passthroughSdr` (`true` vs `false`), `profile` (`Main=1` vs `Main10=2`), EGL config (`8-8-8-8` + no CS vs `10-10-10-2` + `EGL_GL_COLORSPACE_BT2020_LINEAR_EXT`), and MediaFormat color keys (`BT709/Limited/Transfer=3` vs `BT2020/Full/NoTransfer`). `reportGlFailure` NEVER fired (`fault == null` in `002/016`), meaning `eglMakeCurrent`, `draw`, `eglPresentationTimeANDROID`, and `eglSwapBuffers` did NOT throw an exception — or `drain` stalled waiting for frames the encoder silently dropped/refused internally until EOS.

1. **Hypothesis A1 (Strongest — Contract Mismatch on `Main10` Level or EGL `1010102` + `BT2020_LINEAR_EXT`):** `OMX.hisi.video.encoder.hevc` advertises **only `profile=2, level=16777216` (`HEVCMainTierLevel62`)** for Main10 in `inventory.json`, OR Kirin 9020's OMX `RGBA1010102` / `BT2020_LINEAR_EXT` Gralloc consumer silently drops/rejects incoming EGL buffers once frame rendering begins despite `configure(level=16384)` returning `ok`. *(Supported by: `inventory.json` `profileLevels` literally listing `1:1..1:16777216` for Main vs ONLY `2:16777216` for Main10, plus zero `mux` frames despite `129` camera frames and `codec_start ok`.)*

Because `LabRegularLogRunner` forgot to wire `gpu.onRecordedFrame`, we cannot directly tell from logs whether `eglSwapBuffers` was called 120 times and `OMX` never emitted buffers, or whether `renderLatestFrame` skipped `recording`! Wait: `OpenCineLogGpuPipeline.renderLatestFrame()` calls `draw()` + `eglSwapBuffers()` -> if `eglSwapBuffers()` had failed, `reportGlFailure` would have aborted the wait loop (`awaitDuration` checks `fault.get()`), yet `awaitDuration` ran the **full 4.0 s** (`020` -> `025` is `4.46 s`)! ### Failure E: `ISP_TONEMAP_AB` `FLAT` Curve Causing `44%–69%` Highlight Clipping (`008`)
1. **Hypothesis E1 (Most Likely — Gamma/Domain Mismatch + Un-locked AE Interaction):**
   - `PictureProfileCurves.FLAT` (`PictureProfile.kt:11,29`) is explicitly documented as *"Display-referred (sRGB / Rec.709 encoded)"* knots (`0.05 -> 0.08`, `0.18 -> 0.25`, `0.50 -> 0.56`, `0.80 -> 0.84`).
   - In Android Camera2 HAL, `CaptureRequest.TONEMAP_CURVE` typically operates in **linear light BEFORE OETF**, so `(0.50, 0.56)` in sRGB or lifting shadow linear `0.18 -> 0.25` looks radically different once gamma-encoded — **AND** if Huawei's AE metering measures scene brightness or adapts to a brighter lifted midtone without AE lock (`LabSourceProbe` used unlocked `TEMPLATE_RECORD`!), or applies additional DRC/local tone mapping on top of `CONTRAST_CURVE`, highlights saturate at `255` (`44.4%` in R2, `69.0%` in R3).
   - Supporting evidence: When `009` tested `TONEMAP_MODE_GAMMA_VALUE (3)` with `gamma = 2.2`, output was clean and unclipped (`min=19, max=199, mean=101.5, 0% clip`)! And `COLOR_CORRECTION_MODE_TRANSFORM_MATRIX (0)` gave `min=5, max=233, mean=107.3, 0% clip`!
2. **Hypothesis E2:** Manual `TONEMAP_CURVE` requires linear/gentle shoulder knots (`out < in` above `0.2` in linear space, e.g., knee/log-like curve) plus locked `AE_EXPOSURE_COMPENSATION` / manual `SENSOR_EXPOSURE_TIME` + `SENSOR_SENSITIVITY` to test cleanly.
