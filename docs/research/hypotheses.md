## 2. Competing Causal Hypotheses & Evidence Ranking

### Failure A: `LOG_REGULAR_4K30` (`002`, `016`) Configured & Started, Emitted `muxer_track`, Yet Produced `0` Encoded Frames (`3,429 B` MP4)
Note critical comparison: **`003 GPU_HEVC_4K30` uses the exact same `OpenCineLogGpuPipeline` + Camera2 `TEMPLATE_RECORD` + `OMX.hisi.video.encoder.hevc` + same thread/drain loop, and SUCCEEDED (`122–124` frames, `0` drops) in all 3 runs!** Only 4 parameters changed between `003` (works) and `002` (0 frames): `passthroughSdr` (`true` vs `false`), `profile` (`Main=1` vs `Main10=2`), EGL config (`8-8-8-8` + no CS vs `10-10-10-2` + `EGL_GL_COLORSPACE_BT2020_LINEAR_EXT`), and MediaFormat color keys (`BT709/Limited/Transfer=3` vs `BT2020/Full/NoTransfer`). `reportGlFailure` NEVER fired (`fault == null` in `002/016`), meaning `eglMakeCurrent`, `draw`, `eglPresentationTimeANDROID`, and `eglSwapBuffers` did NOT throw an exception — or `drain` stalled waiting for frames the encoder silently dropped/refused internally until EOS.

1. **Hypothesis A1 (Strongest — Contract Mismatch on `Main10` Level or EGL `1010102` + `BT2020_LINEAR_EXT`):** `OMX.hisi.video.encoder.hevc` advertises **only `profile=2, level=16777216` (`HEVCMainTierLevel62`)** for Main10 in `inventory.json`, OR Kirin 9020's OMX `RGBA1010102` / `BT2020_LINEAR_EXT` Gralloc consumer silently drops/rejects incoming EGL buffers once frame rendering begins despite `configure(level=16384)` returning `ok`. *(Supported by: `inventory.json` `profileLevels` literally listing `1:1..1:16777216` for Main vs ONLY `2:16777216` for Main10, plus zero `mux` frames despite `129` camera frames and `codec_start ok`.)*
2. **Hypothesis A2 (Strong — Missing `onRecordedFrame` Telemetry + `HDR` Shader/PBuffer First-Frame Stall or EOS Before Frame 0):** Wait — `021-muxer_track.json` proves `INFO_OUTPUT_FORMAT_CHANGED` fired on the drain thread (`t=44330453` in R2-002), and `024-recorder.json` ran until `t=44334832` (`4.38 s`, `cam=129`). Because `LabRegularLogRunner` forgot to wire `gpu.onRecordedFrame`, we cannot directly tell from logs whether `eglSwapBuffers` was called 120 times and `OMX` never emitted buffers, or whether `renderLatestFrame` skipped `recording`! Wait: `OpenCineLogGpuPipeline.renderLatestFrame()` calls `draw()` + `eglSwapBuffers()` -> if `eglSwapBuffers()` had failed, `reportGlFailure` would have aborted the wait loop (`awaitDuration` checks `fault.get()`), yet `awaitDuration` ran the **full 4.0 s** (`020` -> `025` is `4.46 s`)! That **proves `renderLatestFrame()` either ran all 4 seconds without EGL error (`OMX` swallowed/dropped every `RGBA1010102` frame) OR `recordingFrameMeetsWhiteBalanceBoundary` / `selectedPts` skipped all frames** (check: `minimumSensorTimestampNs = null`, `timelapse = null`, `projectRateOverride = null`, `captureEpoch = null`, so `selectedPts = timestampNs != null`! Thus `eglSwapBuffers` DID run ~120 times and `OMX` output `0` buffers until `CODEC_STOP_TIMEOUT_NS = 5s`!).Wait: `4.46 s` total `020 -> 025`: `4.0 s` record window + `0.4 s` stop = EOS arrived quickly (`<= 0.4s`), NOT 5 s timeout! That means `OMX` received `signalEndOfInputStream()`, processed `EOS` cleanly with `0` video samples emitted, and exited `drain` normally! **Why would HiSilicon OMX emit `INFO_OUTPUT_FORMAT_CHANGED` + immediate `EOS` with `0` encoded frames on an `RGBA1010102` `Surface`?** Either `OMX` rejects `RGBA1010102` + `BT2020_LINEAR_EXT` on input-buffer dequeue/CSC (dropping every queued `GraphicBuffer` inside HAL/Gralloc-to-VENC conversion), OR `OMX` Main10 requires `COLOR_Transfer` / `Level 6.2 (16777216)` / `8-bit EGL` (`forceEgl8BitForMain10=true`) or `COLOR_RANGE_LIMITED`.
3. **Hypothesis A3 (Weak — `HevcVuiTransfer.rewrite` Corrupting IDR/CSD or Causing Drain Rejection):** Unlikely for `0` samples because `muxer_track` succeeded with `csd-0` (rewritten) and `mux=0` means NO non-config frame (including frame 0 IDR) ever left `dequeueOutputBuffer` before `HevcVuiTransfer.rewrite` on IDR would even run (`onSample` is called inside `drainOne`, after `muxer.writeSampleData`). Wait: if frame 0 IDR threw inside `clearTransfer(bytes)`, `drain()`'s `catch` sets `active.failure`, triggering finalization failure with `0` written samples! **Must test synthetic `001` first (fixing `.trimIndent()`):** `001` tests 8 different Main10 EGL/color/level combinations in 2 seconds with zero camera dependency!

**Discriminating Test:** Fix `.trimIndent()` in `LabSyntheticEncoderProbe.kt:504` (1-line fix) + add `Main10 Level 6.2 (16777216)` arm -> immediately isolates `RGBA1010102` vs `EGL8`, `BT2020_LINEAR_EXT` vs `default`, `FULL` vs `LIMITED`, `Level5` vs `Level62`, and whether `HevcVuiTransfer.rewrite` ever throws on IDR.

### Failure D: `AVC 1080p60` (`R2-019` 13 drops, `R3-021` 10 drops) & `R3-018` `1080p30` (1 drop)
1. **Hypothesis D1 (PROVEN Origin — Post-Sensor GPU/SurfaceTexture/AVC-Encoder Drop):** In R2-019, R3-021, AND R3-018, `sensor` had **`0` drops** (`59.925` / `29.991` fps), while `gpuSubmit == muxerInput == mp4File` had exact identical drops (`13`, `10`, `1`).

Note: `E-OCC2-R2-007` (prior run on `d0ffb123`) achieved `1080p60 AVC` at `59.920 fps` (`247` frames, `0` drops), confirming it is borderline GL/encoder scheduling variance, not an absolute 60 fps inability.

### Failure E: `ISP_TONEMAP_AB` `FLAT` Curve Causing `44%–69%` Highlight Clipping (`008`)
1. **Hypothesis E1 (Most Likely — Gamma/Domain Mismatch + Un-locked AE Interaction):**
   - `PictureProfileCurves.FLAT` (`PictureProfile.kt:11,29`) is explicitly documented as *"Display-referred (sRGB / Rec.709 encoded)"* knots (`0.05 -> 0.08`, `0.18 -> 0.25`, `0.50 -> 0.56`, `0.80 -> 0.84`).
   - In Android Camera2 HAL, `CaptureRequest.TONEMAP_CURVE` typically operates in **linear light BEFORE OETF**, so `(0.50, 0.56)` in sRGB or lifting shadow linear `0.18 -> 0.25` looks radically different once gamma-encoded — **AND** if Huawei's AE metering measures scene brightness or adapts to a brighter lifted midtone without AE lock (`LabSourceProbe` used unlocked `TEMPLATE_RECORD`!), or applies additional DRC/local tone mapping on top of `CONTRAST_CURVE`, highlights saturate at `255` (`44.4%` in R2, `69.0%` in R3).
   - Supporting evidence: When `009` tested `TONEMAP_MODE_GAMMA_VALUE (3)` with `gamma = 2.2`, output was clean and unclipped (`min=19, max=199, mean=101.5, 0% clip`)! And `COLOR_CORRECTION_MODE_TRANSFORM_MATRIX (0)` gave `min=5, max=233, mean=107.3, 0% clip`!
2. **Hypothesis E2:** Manual `TONEMAP_CURVE` requires linear/gentle shoulder knots (`out < in` above `0.2` in linear space, e.g., knee/log-like curve) plus locked `AE_EXPOSURE_COMPENSATION` / manual `SENSOR_EXPOSURE_TIME` + `SENSOR_SENSITIVITY` to test cleanly.
